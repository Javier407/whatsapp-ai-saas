Plataforma SaaS multi-tenant

Convertí tu WhatsApp Business en un bot con IA, sin escribir una línea de código.

Un negocio conecta su cuenta de WhatsApp, define flujos conversacionales y carga su base de conocimiento. La plataforma responde a sus clientes automáticamente: por flujos guiados o, cuando no hay flujo, con una respuesta RAG + LLM sobre los documentos del propio negocio.

Visión

Hacia dónde va el proyecto

El núcleo conversacional ya funciona de punta a punta. El camino ahora es pasar de un MVP en modo sandbox de un solo número a una plataforma self-serve, multi-cliente y monetizable: que cualquier negocio se registre solo, conecte su WhatsApp, arme flujos de forma visual y pague por su plan.

Hoy · MVP

Núcleo funcional

Webhooks firmados, motor de flujos con 8 nodos, RAG+LLM, multi-tenancy con RLS y un dashboard operativo. Single-WABA sandbox.

Próximo

Arquitectura

5 servicios desacoplados por Redis Streams

El gateway nunca llama a flow-engine por HTTP: todo el trabajo asíncrono viaja por Redis Streams. Cada servicio sigue arquitectura hexagonal (domain → application → infrastructure → interfaces).

Meta Cloud API (WhatsApp)
  │ webhook firmado (HMAC-SHA256)
  ▼
[ gateway ] Node + Fastify ──┐ resuelve tenant por phone_number_id
                │ Redis Stream flow-engine:{tenant}
                ▼
[ flow-engine ] Python · FastAPI · LangChain (×2 réplicas)
    ├─ ejecuta el grafo de flujo · sesiones en Redis
    ├─ fallback RAG + LLM si ningún flujo matchea
    └─ descifra el token (AES-GCM) y llama Meta Send API

Dashboard (React) ─► [ tenant-api ] Node · Fastify · Prisma
                 │ Redis Stream indexing:{tenant}
                 ▼
[ rag-indexer ] Python worker ─► chunk + embed ─► ChromaDB

Infra: PostgreSQL 16 (RLS) · Redis 7 · ChromaDB · MinIO · Caddy · Loki/Grafana
gateway

Recepción

Verifica HMAC, resuelve el tenant y encola en Redis. Cero lógica de negocio.

tenant-api

API REST

Auth JWT, flujos, base de conocimiento, conversaciones, dry-run. Prisma + RLS.

flow-engine

Cerebro

Ejecuta flujos, RAG y LLM. Resuelve y descifra el token de WhatsApp.

rag-indexer

Indexado

Carga, trocea y vectoriza documentos a ChromaDB con embeddings locales.

Contratos inter-servicio

Dos Redis Streams, una forma acordada

Cada entrada del stream lleva el envelope JSON en su campo data, validado por JSON Schema en infra/contracts/. El gateway nunca llama a flow-engine por HTTP.

📥 flow-engine:{tenant_id}

FlowEngineMessage (gateway → flow-engine)
{
  message_id:  uuid // idempotencia
  received_at: date-time
  tenant_id:   uuid
  phone_number_id: string
  raw: { ...value de Meta Cloud API }
}
// el access_token NO viaja por el stream;
// se resuelve y descifra desde Postgres

📚 indexing:{tenant_id}

IndexingJob (tenant-api → rag-indexer)
{
  job_id:     uuid
  tenant_id:  uuid
  document_id: uuid
  storage_uri: s3://kb-documents/...
  source_type: text|pdf|faq_json|markdown
  embedder:   sbert|openai
  enqueued_at: date-time
}
Política de ACK: mensajes malformados hacen ACK (evitan reencolado infinito); fallos transitorios de dependencias NO hacen ACK. La idempotencia se garantiza con message_id.

Modelo de ejecución

De un mensaje a una respuesta

Secuencia extremo a extremo

1. Meta → POST /webhook → gateway
2. gateway: verifica HMAC-SHA256, resuelve tenant por phone_number_id (cache Redis),
   XADD a flow-engine:{tenant_id}
3. flow-engine (consumer): XREADGROUP → parsea envelope → extrae sender/text de raw.messages[0]
   → carga/crea Session (Redis Hash) → resuelve+descifra access_token (AES-GCM) desde Postgres
4. FlowExecutor: matchea trigger → ejecuta el grafo | si no matchea → fallback RAG+LLM
   avanza nodos hasta wait/end (máx 20 iteraciones → MaxIterationsError)
5. Meta Send API (token descifrado) → history capado a 10 → persiste Session → log → XACK

Máquina de estados de sesión

Redis Hash: session:{tenant_id}:{wa_id}

  IDLE ──match trigger──► IN_FLOW
   │                 │
   │ sin match      fin/error
   ▼                ▼
LLM_FALLBACK  ERROR / IDLE

campos: state · flow_id · current_node
       slots · history[≤10] · retry_count

Disparadores y guardas

  • trigger keyword_match · regex_match · always
  • tope _MAX_ITERATIONS = 20 por mensaje
  • historial _MAX_HISTORY = 10 turnos
  • errores MaxIterationsError · NodeExecutionError → estado ERROR
  • RAG fallback con top_k + umbral de confianza

FlowGraphValidator valida el grafo en el backend: entry node existe, sin nodos huérfanos (BFS), tipos válidos, JMESPath sin patrones peligrosos, URLs sin IPs privadas (SSRF), topes de max_tokens y top_k.

Seguridad

Defensa por capas

MecanismoDóndePropósito
HMAC-SHA256gateway · SignatureVerifierVerifica que el webhook viene de Meta. Comparación en tiempo constante.
JWT HS256tenant-apiAutenticación de sesión del dashboard (12 h por defecto).
AES-256-GCMtenant-api ↔ flow-engineCifra el access_token de WhatsApp en reposo (MASTER_KEY). Se descifra solo en flow-engine, justo antes de llamar a Meta.
argon2idtenant-apiHashing de contraseñas con propiedades memory-hard.
RLS (Postgres)todas las tablas de tenantAislamiento a nivel de fila. ENABLE + FORCE ROW LEVEL SECURITY.
El mecanismo de RLS (y su trampa): cada política es USING (tenant_id = current_setting('app.tenant_id', true)::uuid). Toda transacción debe ejecutar SET LOCAL app.tenant_id = '<uuid>' antes de consultar. Si no se setea, el GUC devuelve NULL, el cast a uuid falla y la política niega el acceso — falla cerrado (fail-closed), no abierto. Dos roles de conexión: app_user (sin BYPASSRLS, runtime) y el migrador (con BYPASSRLS, solo para make migrate).
